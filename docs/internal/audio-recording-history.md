## Согласованное правило будущего голосования

На сайте оцениваются **только описания заданий** (`a`). Рейтинг привязан к
конкретным версиям сравниваемых описаний. Результаты дополнительно объединяются
по **расе и полу говорящего NPC**, формируя предпочтение библиотек для каждой
группы. Это отдельные признаки от `playerVariant`: пол игрока определяет
вариант обращения в тексте, а не группу голоса NPC.

Промежуточные реплики (`p`) и завершение (`c`) выбираются по групповому
предпочтению для NPC, который произносит именно эту реплику. Выдающий и
принимающий NPC могут относиться к разным группам; победитель описания не
закрепляет одну библиотеку за всем заданием. Это рекомендация по группе
говорящего, а не прямая оценка качества конкретного файла `p/c`.

При отсутствии реплики у предпочитаемой библиотеки предполагаемый резерв —
следующая доступная библиотека в той же группе. При неизвестных расе/поле,
неустановленном говорящем или недостатке данных используется обычный порядок
библиотек пользователя. Не подменяй принимающего NPC выдающим для расчёта группы.
При агрегации нужно учитывать набор сравниваемых библиотек, количество оценок
и разнообразие NPC/заданий: простая сумма побед даёт преимущество более частым
участникам. Формула, порог достаточности и применение групповых рекомендаций
к новым версиям файлов должны быть определены перед реализацией рейтингов.

Новая версия описания не наследует прямые оценки старой версии. Для будущего
выбора в аддоне планируется отдельный предварительный рейтинг с ограниченным
вкладом прошлой версии — см. задачу ниже. Историю `p/c`
также сохраняем; обновление этих файлов не сбрасывает оценки неизменившегося
описания. Применение групповой рекомендации к `p/c` не делает их оценёнными.

Таблица охватывает все этапы для независимого учёта изменений файлов.
Выбор по рейтингу в аддоне пока не реализован. Каталог сервера голосования
формата 2 получает из этой таблицы до трёх различных хешей каждой предлагаемой
записи. Приоритет сайта относится к текущему набору подготовленных записей:
сначала неоценённые посетителем, затем с меньшим общим числом оценок, при
равенстве — случайно. Замена одного файла создаёт новое сравнение, а оценки
прежнего набора сохраняются. Установленные у посетителя библиотеки сайт не видит.

## Рассказчики участвуют в сравнении

Уточнение пользователя от 13 октября 2026 года: описания с явным `narrator`
остаются в голосовании при наличии двух или трёх библиотек. Голос сохраняется
для задания и конкретных версий записей, как для остальных описаний. Отсутствие
персонажа не означает отсутствие сравнения.

Общая база помечает такие описания `narrator = true`; сайт показывает свиток и
«Рассказчик». Нельзя приписывать их оценки расе/полу NPC сдачи. Для будущего
общего выбора голоса рассказчика нужна отдельная категория, отличимая от просто
неизвестного говорящего. Текущий экспорт API v2 передаёт нулевой NPC и пустые
расу/пол для обоих случаев; перед внедрением такого группового рейтинга нужно
сохранить явный тип говорящего в контракте экспорта или присоединять его из
версионированного снимка общей базы. По одним пустым расе/полу его не выводить.

## Задача: учитывать прошлые оценки при выборе озвучки в аддоне

Зафиксировано 12 октября 2026 года. Статус: **отложено до реализации обработки
результатов сайта для выбора озвучки в аддоне**. Текущий экспорт и поведение
аддона этим решением не меняются.

Пожелание пользователя: после изменения записи не терять накопленный результат
при расчёте предпочтений. Использовать оценки прежней версии с понижающим
коэффициентом, например **0,5**, вместе со свежими оценками новой версии.
Особенно важно не терять прежнего уверенного лидера только потому, что после
обновления новая запись ещё получила мало голосов.

Направление реализации:

- Исходные голоса остаются привязаны к реально прослушанным хешам и полному
  набору вариантов сравнения. Не переносить их в счётчик прямых оценок нового
  файла и не изменять исторические результаты в БД.
- При неизменном хеше сохранять полный вес оценок независимо от выпуска
  библиотеки. Изменение другого кандидата создаёт новое сравнение; при
  агрегации учитывать состав соперников и не дублировать голоса.
- Для известного нового хеша рассчитывать отдельный предварительный рейтинг
  с ограниченным вкладом предыдущей версии. Неизвестная или неоднозначная
  версия установленной библиотеки не становится известной благодаря этому правилу.
- Не складывать неограниченно все старые голоса с коэффициентом 0,5: большой
  исторический объём может надолго перекрыть результат новой, худшей записи.
  Предложено ограничить наследство **10 условными сравнениями** и постепенно
  убрать его влияние после **20 свежих сравнений**. Коэффициент, лимит, порог
  и формула затухания — гипотезы для проверки, а не утверждённые параметры.
- Пример без дополнительного затухания: старый результат 80/100 после
  коэффициента 0,5 и ограничения до 10 сравнений даёт 8/10; свежий результат
  1/5 даёт предварительно (8 + 1) / (10 + 5) = 60%. Это иллюстрация вклада,
  не готовая формула выбора победителя между произвольными наборами библиотек.
- Пока свежих данных мало, рассмотреть сохранение прежнего лидера как
  предварительного. Обновлённые записи продолжать чаще предлагать на сайте:
  унаследованный рейтинг не должен увеличивать фактическую оценённость
  текущего сравнения и снижать его приоритет в очереди.
- Сравнивать результаты с учётом показанных альтернатив. Предложены попарные
  победы над каждым предложенным соперником для сравнений из двух и трёх
  вариантов; отсутствие голоса не считать поражением.
- В админке разделить свежие оценки, унаследованный вклад и итоговый рейтинг.
  Для игрока с известной старой записью использовать результаты её версии,
  а не подменять их рейтингом нового файла.

Перед реализацией:

- [ ] Определить формулу, порог достаточности, затухание и правила смены лидера.
- [ ] Решить, участвует ли только предыдущая версия или все три поддерживаемые
  версии; исключить повторное наследование уже унаследованных оценок.
- [ ] Определить учёт повторных оценок одного посетителя между версиями и
  сравнениями, где изменился только соперник.
- [ ] Отдельно определить применение этого подхода к группам раса/пол и к
  рекомендациям для `p/c`, которые напрямую на сайте не оцениваются.
- [ ] Проверить на исторических данных сценарии: прежний лидер стал хуже,
  новая запись лучше при малой выборке, изменился только соперник, вернулся
  прежний хеш, у установленной библиотеки неизвестная версия.

Точка входа в реализацию: [экспорт результатов сайта](../../server/voice-vote/RESULTS.md).
Описанная политика относится к будущей обработке экспорта, а не к изменению
сырых голосов или к автоматическому объединению файлов с разными хешами.

## Обновление

Уточнение будущего «выбора сообщества» (13.10.2026): итоговый выбор библиотеки
формируется для сочетания раса–пол, а не для каждого задания отдельно.
Голоса по заданиям и версиям записей остаются исходными данными для расчёта.
Разнообразие выдачи на сайте тоже определяется сочетаниями раса–пол:
случайный выбор с мягким снижением веса недавно показанных групп, без
обязательного полного круга до повтора группы. Внутри группы приоритетны
неоценённые пользователем сравнения, затем сравнения с меньшим числом голосов.

Все три импортёра аудиометаданных автоматически дополняют историю после
успешной генерации своего манифеста:
`generate-classic-metadata.js`, `import-forever-audio.js`,
`generate-wayfarer-metadata.js`. Каждый обновляет только обработанные пакеты.
Отсутствие установленного пакета Wayfarer не удаляет его прежнюю историю.

Для сверки истории со всеми текущими манифестами:

```shell
node tools/audio-recording-history.js --check
```

Для добавления уже проверенных манифестов в историю:

```shell
node tools/audio-recording-history.js
```

Команды читают метаданные, а не установленные OGG. Перед первоначальным
снимком версии и SHA-256 всех 25 961 файлов сверены с установленными пакетами.
При дальнейших обновлениях фактические файлы проверяются импортёрами и
сверками из скилла `update-libraries`. Не удаляйте историю перед импортом:
текущий манифест не содержит прошлых снимков. Повторный импорт идентичных
данных не меняет таблицу; `--check` ничего не записывает. Проверка включена
в `node tests/run.js` и общий `Test`.

## Формат

- `identity: file-sha256`: идентичность по полным байтам OGG, не по имени,
  размеру, длительности или номеру релиза.
- `supportedRevisionsPerFile: 3`: окно трёх последних различных версий
  каждого файла для будущего применения оценок. Полная история остаётся
  в JSON; старые сведения не удаляются при выходе из окна.
- `packs`: отдельные записи для реальных пакетов, включая независимые
  Alliance/Horde/Shared/Narrator у Wayfarer.
- `releases`: снимки проверенных выпусков в порядке первого наблюдения.
  `version` — номер библиотеки; `snapshotSha256` — отпечаток номера версии
  и отсортированной карты `путь → SHA-256`. Это не хеш ZIP.
- `currentRelease`: номер текущего импортированного снимка, начиная с 1.
- `recordings`: пути относительно каталога аудио пакета. Для CatQuest —
  относительно `Sounds/q`, для WowVoiceSounds и Wayfarer — корня пакета.
- Каждая запись содержит `questID`, `section` (`a`, `p`, `c`),
  `playerVariant` (`common`, `male`, `female`) и `revisions`.
  Вариант отражает обращение к полу **игрока**, а не пол говорящего NPC.
- Версия записи содержит `sha256`, `bytes`, `duration` и `releases` —
  номера всех проверенных снимков, в которых находился именно этот файл.
  Отсутствие номера означает, что файл в том снимке отсутствовал.

Смена выпуска библиотеки без изменения файла добавляет только связь с новым
снимком. Новый SHA-256 создаёт отдельную версию. Возврат прежних байтов
повторно использует их версию; при расчёте окна учитывается последнее
появление каждой версии в новых проверенных снимках. Повторное чтение уже
известного старого выпуска не меняет порядок истории.

Если под одним номером библиотеки обнаружены разные снимки, сохраняются оба.
По одному номеру TOC такой выпуск неоднозначен; нельзя выбирать один из
снимков как достоверный. Неизвестный выпуск также не наследует старые оценки.
Функция `resolve` возвращает `known` с SHA-256, `unknown-release`,
`ambiguous-release`, `absent` или `outside-history-window`. `known` означает
известную идентичность, а не наличие рейтинга. Это инструмент подготовки
данных на Node.js, не реализация выбора озвучки внутри игры.

## Границы проверки

Начальная реализация сравнивает хеш **файла**. Изменение тегов OGG или
повторное кодирование тоже создаёт новую версию. Декодирование PCM и
объединение побитно разных файлов с одинаковым звучанием пока не реализованы;
автоматически переносить оценки между ними нельзя.

Аддон не вычисляет SHA-256 OGG в игре. Будущее сопоставление по версии пакета
применимо к проверенным неизменённым выпускам. Незаметно заменённый файл при
сохранённом TOC нельзя обнаружить по этой таблице на компьютере пользователя.
Для точного различения таких сборок нужны идентификаторы от авторов пакетов.
После обновления пакета до неизвестной версии старый рейтинг не применяется.
